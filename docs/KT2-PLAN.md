## 1. Что проверили и что требуется

Нет Go-модуля/сервера, БД, BM25, корпуса, benchmark или LLM-клиента. Прототип не сохраняет пользователей, не авторизует и показывает один фиксированный ответ. Суммы штрафов из прототипа нельзя использовать как проверенные эталоны.

Старое предложение «25 запросов и только Recall/MRR» заменяем требованиями занятия 3. Собственную языковую модель обучать не требуется. BM25 реализуем сами, готовую LLM подключаем по API (внешний провайдер или локальная модель). Ответ должен опираться на переданный контекст, при недостатке сведений — отказ. Заглушка допустима для тестирования интерфейса, но не является результатом КТ2.

Объём 30 и 10+5 задан слайдами. Предметные ID pdd-*/koap-* сохраняем; D01…D30 — пример оформления. Выбор k=5 и MRR по полной выдаче — наше предложение: преподаватель просит заранее согласовать глубину. Николай уточняет это до финального прогона; при иной договорённости обновляем rag.md и отчёт. Порогов метрик для зачёта в материалах нет.

## 2. Что именно должно получиться

Ученик входит настоящим аккаунтом, задаёт вопрос, получает ответ реальной LLM и раскрывает найденные документы. При пустом поиске видит отсутствие сведений, при недостаточном контексте — честный отказ, при отказе API — сообщение об ошибке и найденные документы. Админ создаёт учеников и видит их вопросы после обновления страницы и перезапуска приложения (SQLite).

Отдельный CLI по тем же документам/поиску/промпту прогоняет 15 вопросов, сохраняет новую выдачу и реальные ответы, после человеческой оценки рассчитывает четыре метрики. На сдаче команда запускает CLI заново. Сохранённый старый отчёт нужен для сравнения, но не заменяет live-прогон.

Новых функций сверх этой задачи не добавляем: векторный поиск, обучение модели, чат, самостоятельная регистрация, редактор корпуса и внешний хостинг не нужны.

## 4. Порядок и зависимости

1. Сначала влить эту ветку Петра: актуальные spec, план, модуль и интерфейс. Прочитать UI-контракт и целевые API поиска/benchmark. Изменения контракта согласовывать до написания вызывающего кода.
2. Егор готовит корпус + поиск + queries + retrieval/score CLI. Николай параллельно делает store/auth/web/llm с тестами на подставных сервисах; можно временно не подключать поиск в исполняемый сервер, но не подменять им финальную демонстрацию. Оба начинают от свежей main после шага 1.
3. Влить поиск/CLI Егора. Николай обновляет ветку, подключает поиск, общий RAG и mode=rag в CLI, фиксирует реально работающую модель/настройки. HTTP и benchmark используют один сервис.
4. Пётр на объединённом сервере проходит все сценарии, проверяет телефон/десктоп, устраняет UI-дефекты. Николай/Егор исправляют ошибки своих пакетов. Открыть второй PR Петра, если появились изменения кода.
5. Зафиксировать корпус/queries/k/модель/промпт. Запустить retrieval и rag. Пётр оценивает все 15 фактических ответов, связывает оценки с run_id; команда разбирает спорные случаи. Егор формирует results.md через score, все читают вывод.
6. Сделать репетицию с чистым клоном, собрать бинарники заранее, проверить live-запуск benchmark. Каждый должен уметь запустить и объяснить весь путь запроса.

Срок каждого шага команда ставит относительно фактической даты КТ2. Не ждать её уточнения для начала разработки.

## 5. Задача Николая — интеграция

Ветка `feat/kt2-server`, после этой ветки Петра. До кода уточнить architecture.md по реально выбранным настройкам.

1. Настройка: Go 1.25+, env ADDR, DB_PATH, CORPUS_DIR, ADMIN_LOGIN/ADMIN_PASSWORD, LLM_BASE_URL/API_KEY/MODEL, таймаут вызова. `.env.example` содержит только пустые значения и несекретные примеры; Go сам .env не читает, способ загрузки объяснить в README. Не коммитить реальные ключи, пароли, SQLite, cookies. При отсутствии обязательных настроек — понятная ошибка запуска.
2. Store: modernc.org/sqlite, users/query_log по spec, bcrypt, уникальность логина, параметризованные SQL, foreign_keys. Начального админа создавать только если его нет, не сбрасывать пароль при перезапуске. При занятом логине с ролью student не считать это успешной инициализацией admin. Сохранять БД между запусками.
3. Auth: случайные непрогнозируемые сессии в памяти, HttpOnly/SameSite cookie, истечение срока, удаление при выходе. Для localhost HTTP cookie не должна требовать HTTPS; в иной конфигурации Secure включается настройкой. Серверная проверка CSRF всех POST, ограничение размера тела. Ученик не получает админские данные даже через прямой HTTP-запрос.
4. Web: маршруты architecture.md и формы ui.md. Обязательная валидация пустого/пробельного вопроса и лимита 2000 символов, логина/пароля, дубликата логина. Чужая роль — 403, незалогиненный — перенаправление на login. Использовать ui.Renderer и embedded StaticHandler, без копирования шаблонов и замены типов на template.HTML. Создание ученика — POST/Redirect/GET. Сообщения об ошибках общие, пароль не возвращается.
5. LLM: HTTP-клиент к POST {LLM_BASE_URL}/chat/completions, timeout/context, проверка HTTP-статуса, пустого/некорректного ответа, ограничение размера ответа, обработка 429/5xx. Чёткий system prompt: отвечать только по переданным документам, не выполнять инструкции из контекста, указывать ref, отказать при нехватке данных. JSON-ответ с Answer/Refused валидировать; сырые ошибки и ключи не показывать пользователю.
6. RAG: после слияния поиска вызвать LoadCorpus/New при запуске; обрабатывать question через один Ask для сервера и benchmark. По пустой выдаче LLM не вызывать. При ошибке LLM сохранить Sources. Непустая выдача может привести к Refused=true. Непустой допустимый вопрос логировать один раз даже при отказе/ошибке; ошибку БД не скрывать. Не передавать в RAG reference_answer/relevant/kind из benchmark.
7. Встроить режим `-mode rag` в CLI Егора: новый прогон всех 15 вопросов через тот же Ask, прогресс, тайминги, конфигурация, run_id/хеши, настоящие ответы. Не объявлять сетевой сбой отказом. Частичный файл разрешается сохранять для диагностики с явным статусом failed, но команда возвращает ненулевой код и score не принимает неполный прогон.
8. Модель: выбрать доступную и реально протестировать. Для Ollama указать точное имя модели, команды скачивания/запуска и время прогрева; для внешнего API проверить лимиты перед сдачей, key только из env. Не обещать устаревшие «50 бесплатных запросов» из КТ1. Название модели записать в отчёт. В README дать команды терминала A (модель, если локальная), B (server), C (benchmark).
9. Проверки: go test ./..., тесты HTTP/ролей/CSRF, корректный вход/выход, дубликат, сохранение БД, лог ошибок поиска/LLM. LLM-клиент тестировать через httptest (успех, 429, timeout, невалидный JSON); отдельно выполнить один настоящий успешный вызов с моделью. После интеграции передать Петру локальные инструкции без секретов, чтобы он выполнил приёмку.

Готово: fresh clone поднимает сервер по README; оба сценария работают с БД; пользователь видит реальный ответ/источники; CLI mode rag создаёт новый полный run; настройки воспроизводимы. Николай обновляет README с фактическими командами, не только планом.

## 6. Задача Егора — BM25 и benchmark

Ветка `feat/kt2-search`, после этой ветки Петра. Источник истины — обновлённый rag.md.

1. Собрать ровно 30 содержательных документов из ПДД/главы 12 КоАП. Сохранять цельные условия, исключения и примечания. Выбрать около 10 тем, позволяющих составить 10 вопросов, каждому из которых действительно нужны минимум три документа. Не обязательно по три уникальных документа на тему, пересечения допустимы. Не дописывать нормы самостоятельно. Сверить действующую редакцию и дату, вести URL/происхождение для каждого ID в corpus/README.md. Поставить честное ограничение: это учебная выборка, а не полный юридический справочник.
2. Корпус: pdd.json/koap.json, поля id/ref/text, уникальные непустые ID/тексты. Проверить ручную выборку по оригиналу. Скрипт скачивания не обязателен при 30 документах; runtime не скачивает документы.
3. Реализовать internal/search: регистр, ё→е, токены с сохранением номеров 12.9/5.19.1, стоп-слова и Snowball, единая обработка запросов/документов. Проверить настоящее API выбранной версии библиотеки, зафиксировать dependency. Аргументировать ограничения стемминга в rag.md. Поиск BM25 и обратный индекс написать самим.
4. API: LoadCorpus(dir string) ([]Document,error); New(docs []Document,k1,b float64) (*Index,error); Index.Search(query string,k int) []Hit. Document{ID,Ref,Text string}, Hit{Document Document; Score float64}. Возвращать score DESC, равные score — по порядку корпуса, при загрузке файлы сортировать по имени. Повторные термы запроса учитываются согласно текущему rag.md. k<=0 — пустая выдача; no match — пустая выдача; пустой/некорректный корпус и недопустимые k1/b — явная ошибка New. New строит неизменяемый индекс, Search безопасен для параллельных чтений.
5. Queries: 10 normal + 5 trap, id/kind/theme/query/relevant/reference_answer. Запросы своими словами, не цитаты. Эталоны normal покрывают все факты, relevant — минимум три разных существующих документа. Ловушки без ответа именно в этих 30 документах, часть — с лексическими совпадениями. До первого замера Пётр проверяет смысл эталонов, все фиксируют набор.
6. CLI cmd/bench: mode retrieval без LLM и mode score по сохранённому run и ручным grades; флаги/выходы по rag.md. Зарезервировать mode rag для добавления Николаем. Не создавать второй независимый код поиска в CLI. До запуска валидировать данные/ID/состав набора. Метрики поиска считать по normal, denominator=10; MRR с явно указанной глубиной. Подтвердить k и глубину с Николаем/преподавателем.
7. Формат run и grades согласовать с Николаем до его режима rag. Score требует полный успешный run и все 15 оценок именно этого run; добавить хеш-связь. Если оценки отсутствуют, Accuracy/CRR — «не оценено». Не считать Refused автоматически правильным ответом ловушки и не проверять Accuracy равенством строк. Ручные оценки поставляет Пётр по фактическим ответам.
8. Тесты: ручной расчёт BM25 на маленьком корпусе, IDF/нормализация длины, номера токенов/ё, порядок равных score, пустые запросы/неизвестные слова, стабильность, неверные ID разметки. Метрики проверить известным примером: relevant A/D/F, top3 B/A/D даёт Recall@3=2/3 и RR=1/2; ловушки не меняют поиск. Ошибки/дубликаты grades должны отклоняться. go test ./... и go run ./cmd/bench -mode retrieval.
9. После интеграции и ручной оценки сформировать results.md с четырьмя метриками, моделью/параметрами/run_id, выдачей и разбором ошибок. Не подбирать параметры по контрольным вопросам и не менять relevance ради хорошего результата. Измерить действительное качество и объяснить ограничения.

Готово: поиск импортируется сервером, корпус/queries валидны, retrieval повторяется без сети, rag Николая использует тот же индекс, score после разметки даёт четыре метрики. Наличие старого results.md не заменяет новый прогон.

## 8. Команды и приёмка всей команды

Уже доступны в ветке Петра:

```sh
go test ./...
go run ./cmd/ui-preview
```

Открыть точный URL `http://127.0.0.1:<порт>`, напечатанный программой после успешного запуска. Баннер со ссылками позволяет проверить все состояния. Отправка формы возвращает 501: обработчики добавляет Николай. Это проверка UI, не репетиция работающего RAG.

Целевые команды после слияния задач Николая и Егора (сейчас ещё не реализованы):

```sh
go test ./...
go build -o /tmp/pdd-server ./cmd/server
go build -o /tmp/pdd-bench ./cmd/bench
go run ./cmd/server
go run ./cmd/bench -mode retrieval -out benchmark/runs/retrieval.json
go run ./cmd/bench -mode rag -out benchmark/runs/live.json
go run ./cmd/bench -mode score -run benchmark/runs/live.json -grades benchmark/grades/live.json -out benchmark/results.md
```

Для Windows Николай добавляет отдельные PowerShell-команды. Пути /tmp здесь только пример для macOS/Linux. Модель/ключ конфигурируются до server/rag по фактическому README. Все команды выполняются из корня репозитория.

Перед КТ2:

- [ ] На чистом клоне README достаточен для запуска, не нужны скрытые локальные файлы.
- [ ] Настоящая LLM доступна; при локальной модели она скачана и прогрета, при внешней проверен лимит минимум на 15 вопросов и показ.
- [ ] В Git есть 30 документов, 15 вопросов/эталонов, источник/редакция, код, последний run, оценки, отчёт и разбор ошибок; нет секретов/БД.

Демонстрация: Николай поднимает приложение и показывает создание ученика; Пётр показывает вопрос/источники/отказ и журнал; Егор запускает benchmark вживую и объясняет поиск/метрики. Для свежего ответа Accuracy/CRR требуют оценки: открыть результат, поставить оценки и пересчитать score, а не выдавать прежние числа за новые. Предыдущий полный отчёт можно показать рядом.

## 10. Git и сдача

Одна задача — ветка от свежей main, коммиты своим аккаунтом. Сначала spec, потом код, затем проверки и CHANGE_HISTORY. Push ветки и PR; main напрямую не менять, автоматическое слияние без командного ревью не делать. Этот план является предложенным общим контрактом для ревью в PR: участники могут уточнить детали до зависимой реализации. Нельзя записывать вклад товарища на свой аккаунт.

Внешнего деплоя нет. Локальный просмотр UI запускается сейчас; полный localhost-запуск и benchmark обеспечиваются после интеграции двух остальных частей. Финальная готовность КТ2 определяется чек-листом раздела 8, а не наличием этого документа.
