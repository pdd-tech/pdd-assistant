# Приёмка КТ2

Проверки preview выполнены 20.11.2026. Финальную локальную приёмку и разметку принимает на себя Николай. Результаты интеграционной проверки от 21.11.2026 приведены ниже.

## Уже проверено в ветке интерфейса

- `go test ./...`: рендеринг всех экранов/состояний, экранирование вопроса, ответа, логина, текста/ID источников и сообщений; формы/CSRF; пустые списки; неизвестный экран/состояние возвращают ошибку до записи ответа; embedded CSS/JS; preview отклоняет POST статусом 501.
- `go test -race ./...`: общий Renderer допускает параллельный рендеринг без гонок.
- `go vet ./...`: без замечаний.
- Локальный браузер: пробельный вопрос отклонён с сообщением; непустой вопрос отправляется POST и получает честное объяснение ограничений preview; после Back кнопка вновь доступна; текст источника раскрывается; при отказе/сбое модели документы остаются видимыми.
- При ширине 375 px форма админки читается, ширина документа 375 px, широкая таблица прокручивается внутри контейнера (420 px в контейнере 309 px).
- Просмотр не использует внешнюю сеть, БД, LLM или секреты. Команда запуска из корня: `go run ./cmd/ui-preview`.

## Приёмка benchmark и ручная оценка

Прогоны, оценки всех 15 ответов и разбор ошибок связаны в [отчёте benchmark](../benchmark/results.md). Для финальной локальной версии ответы оценены Codex по поручению Николая.

1. Проверить происхождение 30 документов и разметку 10 normal + 5 trap; для normal минимум 3 различных relevant и эталон полного ответа. Не использовать демонстрационные тексты preview.
2. Согласовать с преподавателем k/глубину MRR, записать параметры в rag.md. Перед прогоном зафиксировать SHA корпуса и questions.
3. Выполнить новый retrieval, затем новый rag через общий сервис приложения. Должны появиться ответы/источники всех 15 вопросов, модель/настройки/run_id/хеши/время. Ошибки API не маскируются под отказы, неполный прогон не считается завершённым.
4. Ответственный за оценку читает каждый ответ вместе с фактическими sources и reference_answer. Для normal correct=true только при всех верных фактах, отсутствии неподтверждённых утверждений и корректных ссылках. Перефразирование допустимо. Частично правильный ответ — false с объяснением.
5. Для trap correct=true только при содержательном отказе без попытки додумать ответ. Один лишь флаг Refused недостаточен: прочитать текст. Таймаут, пустой ответ, «нет сведений, но вероятно…» — false.
6. В grades внести все 15 ID, correct/comment, run_id и SHA256 проверенного run. Не переносить оценки с другого запуска, даже при тех же вопросах. В спорных случаях сверить исходный вопрос, эталон и фактический контекст.
7. Score сверяет соответствие и вычисляет Recall@5/MRR по 10 normal, Accuracy=correct_normal/10, CRR=correct_trap/5. Проверить числители вручную. Отчёт содержит параметры и 2–3 конкретных примера ошибок, без выдуманных результатов.
8. На репетиции и сдаче снова выполнить новый benchmark в терминале. Запуск старого JSON/открытие results.md не является runtime benchmark. Новый run требует новой ручной оценки для метрик ответов; метрики поиска считаются автоматически.

Повторная проверка запуска: default `127.0.0.1:0` получает свободный порт ОС; при намеренно занятом адресе программа завершается ненулевым кодом без сообщения об успешном старте. Содержимое страницы, заголовок pdd-assistant и CSS/JS сверены на фактически выделенном порту. Соседние сервисы Docker/pgAdmin не останавливаются.

## Показ интерфейса

1. Загрузить окружение API, проверить доступность модели и остаток квоты, затем открыть URL из лога сервера. Войти админом и создать отдельного ученика для показа.
2. Войти учеником, задать обычный вопрос и раскрыть источники. Показать, что программа подставляет ссылки на документы из выдачи BM25.
3. Задать ловушку с непустой выдачей. Показать явный отказ и сохранённые документы. Вернуться админом и найти оба вопроса в журнале.
4. Во втором терминале загрузить тот же `.env` и запустить `rag` командами из README. Пока модель отвечает, открыть сохранённый отчёт и объяснить четыре метрики и два примера ошибок. Сохранить новый run отдельно и оценить полученные ответы.


## Переход на Gemini API

21.11.2026 по запросу Петра локальный Ollama заменяется внешним API. Попытки OpenRouter сохранены отдельно: Lightning прерван после 7 вопросов; полный прогон Super VL завершил 15 вопросов, но 5 ответов не прошли проверку формата. Эти файлы имеют status=failed и не подтверждают готовность КТ2.

Затем команда выбрала Gemini 2.5. Ключ Google действителен, модель перечислена в каталоге, однако нативная генерация обоих вариантов 2.5 Flash и Flash-Lite вернула HTTP 404: модель недоступна новым пользователям. После этого Пётр явно согласовал Gemini 3.8 Flash. Проверки Chromium и оценки Qwen выше относятся к прежнему профилю, а не к Gemini.

Новый клиент проверяет обязательные поля по JSON Schema, ID источников и дословные цитаты; поддерживает опциональную генеративную проверку. Ключи остаются в игнорируемом .env. Результаты реального Gemini benchmark и интеграционной проверки фиксируются отдельно после выполнения; успешные unit-тесты не заменяют их.


## Переход на GigaChat

По последнему запросу Петра закреплён GigaChat API, модель GigaChat-2-Max и действующий официальный адрес https://gigachat.devices.sberbank.ru/api/v1. Authorization key успешно обменивается на Access token; модель присутствует в списке доступных. API balance показал выданную квоту Max. Пакеты не приобретались, системные настройки TLS не менялись.

Клиент кэширует токен до истечения срока и обновляет его; проверка сертификатов включена, публичный корневой сертификат добавляется только в HTTP-клиент приложения. JSON Schema передаётся в формате GigaChat, а ID и цитаты проверяются клиентом. Интерфейс и benchmark используют одну конфигурацию.

После добавления OAuth прошёл go test ./..., включая кэширование/обновление токена, конкурентные запросы, отмену ожидания и формат схемы. По прямому указанию Петра последующие проверки и запуски остановлены. Успешный полный benchmark GigaChat, его разметка и повторная браузерная приёмка здесь не заявляются. Сохранённые старые результаты не относятся к этой модели.
