# Поиск (RAG)

Как устроен поиск документов по вопросу ученика и как мы проверяем его качество. Место поиска в общем пути запроса описано в `spec/tech/architecture.md`, шаг 4.

## Корпус

### Источники

| Что | Документ | Откуда берём |
|---|---|---|
| ПДД | Правила дорожного движения РФ (Постановление Правительства РФ от 23.10.1993 № 1090) | https://www.consultant.ru/document/cons_doc_LAW_2709/ |
| КоАП | Кодекс РФ об административных правонарушениях, глава 12 «Административные правонарушения в области дорожного движения» | https://www.consultant.ru/document/cons_doc_LAW_34661/ |

К КТ2 готовим фиксированную учебную выборку из **30 документов**, по слайдам занятия 3, с. 39. Егор записывает дату редакции и URL источника каждого документа в `corpus/README.md`. Полное покрытие нормативных актов переносится за рамки КТ2. В интерфейсе явно обозначается учебный объём базы.

Допустимые источники для выборки:
- разделы 1–26 ПДД;
- статьи главы 12 КоАП (12.1–12.37, включая статьи вида 12.21.1).

Не входят: приложения к ПДД (дорожные знаки и разметка), «Основные положения по допуску транспортных средств к эксплуатации», перечень неисправностей и остальные главы КоАП.

### Разбиение на документы

- **ПДД:** один пункт = один документ, вместе со своими подпунктами и перечнями. Например, п. 11.4 «Обгон запрещен:» вместе со списком мест, где обгон запрещён.
- **Исключение — п. 1.2 ПДД.** Это перечень из 64 терминов («Обгон», «Стоянка», «Перекресток» и т.д.). Целиком он был бы самым длинным документом корпуса и совпадал бы почти с любым запросом. Поэтому каждый термин п. 1.2 — отдельный документ.
- **КоАП:** одна статья = один документ, со всеми частями и примечаниями. Название статьи входит в текст документа.
- Пункты и статьи с текстом «Утратил силу» / «Утратила силу» в корпус не попадают.
- Служебные пометки КонсультантПлюс (`(в ред. Постановления ...)`, `(см. текст в предыдущей редакции)`) из текста удаляются.

### Формат

Корпус лежит в папке `corpus/` (переменная `CORPUS_DIR`) двумя файлами: `pdd.json` и `koap.json`. Каждый файл — массив документов:

```json
[
  {"id": "pdd-11.4", "ref": "ПДД, п. 11.4", "text": "Обгон запрещен: на регулируемых перекрестках, ..."},
  {"id": "pdd-1.2/Обгон", "ref": "ПДД, п. 1.2, термин «Обгон»", "text": "\"Обгон\" - опережение одного или нескольких ..."},
  {"id": "koap-12.15", "ref": "КоАП РФ, ст. 12.15", "text": "Нарушение правил расположения транспортного средства ..."}
]
```

- `id` — уникальный идентификатор, на него ссылается benchmark.
- `ref` — ссылка для человека. Её видит ученик в списке найденных документов, и она же подставляется в промпт LLM.
- `text` — текст документа. По нему ищем, его же передаём в LLM.

Готовые `pdd.json` и `koap.json` с суммарно 30 документами коммитятся в репозиторий: запуск сервера и benchmark не требует скачивания корпуса. При таком объёме допускается ручная подготовка с проверкой по источнику; обязательный отдельный сетевой скрипт `cmd/corpus` из плана КТ1 отменён. Идентификаторы `pdd-*`/`koap-*` сохраняем: D01…D30 в слайдах — пример стабильных ID, а не требование переименовать предметные ссылки.

## Предобработка текста

Документы и запросы проходят одну и ту же предобработку (методичка, замечание 1.1). Шаги по порядку:

| Шаг | Что делаем | Почему |
|---|---|---|
| 1. Регистр | Приводим к нижнему регистру | Заглавная буква в начале предложения или в термине («Обгон») не меняет смысл слова |
| 2. Буква «ё» | Заменяем «ё» на «е» | В ПДД и КоАП пишут «е», ученики пишут по-разному. Стеммер их различает: «перекрёсток» и «перекресток» дают разные основы |
| 3. Токенизация | Токен — непрерывная последовательность букв и цифр. Число с точками внутри (`12.9`, `5.19.1`) — один токен. Всё остальное (пробелы, знаки препинания, кавычки, дефисы) — разделители | Слово — естественная единица для BM25. Номера пунктов, статей и знаков важны: ученик может спросить «что говорит статья 12.9», и если резать по точке, получатся бессмысленные токены `12` и `9` |
| 4. Стоп-слова | Удаляем слова из стандартного списка Snowball для русского языка (`russian.IsStopWord` из `kljensen/snowball`, около 150 слов: «и», «на», «не», «ли», «можно», «нельзя», «при» ...) | Эти слова есть почти в каждом документе и вопросе и почти не помогают отличить нужный документ. Отрицание «не» теряется, но BM25 всё равно не понимает отрицаний — смысл восстанавливает LLM, которая читает исходный текст документа |
| 5. Стемминг | Отрезаем окончания стеммером Snowball для русского языка (`github.com/kljensen/snowball`) | См. ниже |

### Стемминг вместо лемматизации

Методичка разрешает лемматизацию готовой библиотекой или отказ от неё, выбор нужно обосновать.

Мы используем **стемминг**, а не лемматизацию:
- Для Go нет зрелого лемматизатора русского языка. Хорошие лемматизаторы (pymorphy, Mystem) — это Python-библиотека или отдельная программа, их пришлось бы запускать вторым процессом рядом с Go-сервером.
- Стеммер Snowball написан на чистом Go, работает быстро и всегда даёт одинаковый результат.
- Для поиска не нужна правильная начальная форма слова, нужно только, чтобы разные формы одного слова совпадали. В большинстве случаев стеммер с этим справляется.

Минусы стеммера мы проверили на словах из нашей предметной области (`kljensen/snowball` v0.10.0):

| Слова | Основы | Итог |
|---|---|---|
| мост, мосту, мостах | мост | совпадают |
| штраф, штрафа, штрафом | штраф | совпадают |
| пешеход, пешехода | пешеход | совпадают |
| обгон, обгоне / обгонять, обгоняющего | обгон / обгоня | **не совпадают** |
| перекресток / перекрестке | перекресток / перекрестк | **не совпадают** (беглая гласная) |

Из-за таких ошибок часть релевантных документов может не найтись. Насколько это влияет на качество, покажет benchmark, это войдёт в вывод.

### Пример

Запрос «Можно ли обгонять на мосту?»:

1. нижний регистр: `можно ли обгонять на мосту?`
2. токены: `можно`, `ли`, `обгонять`, `на`, `мосту`
3. без стоп-слов: `обгонять`, `мосту`
4. после стемминга: `обгоня`, `мост`

П. 11.4 ПДД («Обгон запрещен: ... на мостах, путепроводах, эстакадах ...») совпадёт с запросом по терму `мост`, а по терму `обгоня` не совпадёт: в пункте слово «обгон» даёт основу `обгон`.

## Индекс

Индекс строится в памяти при запуске сервера из файлов корпуса (см. `spec/tech/architecture.md`). Корпус КТ2 — 30 документов, поэтому хранить индекс на диске не нужно.

Что хранит индекс:
- список документов: `id`, `ref`, `text` и длина `|d|` в термах после предобработки;
- обратный индекс: для каждого терма — список пар (документ, `TF(t, d)`), где `TF(t, d)` — сколько раз терм встречается в документе;
- число документов `N` и среднюю длину документа `avgdl`.

`DF(t)` — длина списка документов терма `t`.

## Ранжирование BM25

Формулы взяты из методички (раздел 1.3).

```math
\mathrm{IDF}(t) = \ln\left(1 + \frac{N - \mathrm{DF}(t) + 0.5}{\mathrm{DF}(t) + 0.5}\right)
```

```math
\mathrm{BM25}(q, d) = \sum_{t \in q} \mathrm{IDF}(t) \cdot \frac{\mathrm{TF}(t, d)\,(k_1 + 1)}{\mathrm{TF}(t, d) + k_1\left(1 - b + b\,\frac{|d|}{\mathrm{avgdl}}\right)}
```

- `q` — термы запроса после предобработки. Если терм повторяется в запросе, он учитывается столько раз, сколько встречается.
- Считаем оценку только для документов, в которых есть хотя бы один терм запроса (их берём из обратного индекса). У остальных оценка 0, и в выдачу они не попадают.
- Документы сортируются по убыванию оценки, при равной оценке — по порядку в корпусе, чтобы выдача была одинаковой при каждом запуске.

### Параметры

| Параметр | Значение | Почему |
|---|---|---|
| `k1` | 1.2 | Нижняя граница типичного диапазона 1.2–2.0 из методички. Повтор слова в коротком пункте ПДД не должен слишком сильно поднимать документ |
| `b` | 0.75 | Значение, которое методичка называет типичным. Длины документов сильно различаются: определение термина — одно предложение, статья КоАП — несколько частей. Без нормализации по длине длинные статьи выигрывали бы за счёт количества слов |
| `k` (top-k) | 5 | Столько документов поиск отдаёт в промпт LLM. Для обычного вопроса размечаем минимум 3 релевантных документа; top-5 ограничивает объём контекста. Значение k согласуем до сдачи |

Если в запросе после предобработки не осталось термов или ни один документ не совпал, поиск возвращает пустой список.

## Benchmark КТ2

Этот раздел заменяет план КТ1 с 25 вопросами. Основание: занятие 3, слайды 37–43; методичка, раздел 2, с. 8; дополнительное сообщение преподавателя о запуске в рантайме. Объём 30 документов и 10 + 5 вопросов взят из занятия 3, а не из методички (она не задаёт количество запросов).

### Данные

`benchmark/queries.json` — ровно 15 записей: 10 `normal` и 5 `trap`. Формат для реализации Егором:

```json
[
  {
    "id": "q01",
    "kind": "normal",
    "theme": "Тема из корпуса",
    "query": "Составной вопрос ученика своими словами",
    "relevant": ["id-1", "id-2", "id-3"],
    "reference_answer": "Все факты, необходимые для полного ответа"
  },
  {
    "id": "t01",
    "kind": "trap",
    "theme": "Отсутствующие сведения",
    "query": "Вопрос, на который выбранные документы не отвечают",
    "relevant": [],
    "reference_answer": "В документах нет этой информации"
  }
]
```

Каждый обычный вопрос имеет не менее 3 различных релевантных ID. Для этого задаём содержательные вопросы, которым действительно нужны три документа, а не добавляем определения без необходимости. Все обычные вопросы имеют эталон полного ответа. Ловушки могут содержать слова из корпуса: нужно проверять недостаточность сведений даже при непустом top-k. Распределяем вопросы между темами выбранных 30 документов; не обещаем покрытие всех разделов ПДД. Разметку сверяют люди до первого измерения. Запросы формулируются своими словами. Контрольные вопросы не используем для подбора параметров.

До выполнения benchmark валидирует: 30 уникальных непустых документов, 15 уникальных ID вопросов, состав 10/5, непустые эталоны, минимум 3 различных существующих relevant у normal, пустой relevant у trap. Ошибки формата завершают процесс ненулевым кодом.

### Метрики

Проектное предложение перед согласованием с преподавателем: `k=5` и MRR по полной выдаче (до 30 документов); фиксируем именно эту глубину в отчёте. Слайд 43 требует согласовать k и глубину MRR заранее. Если преподаватель задаст MRR@5, меняем спецификацию и явно называем метрику MRR@5. Не смешиваем определения между прогонами.

- **Recall@5**, среднее по 10 normal: `sum(|relevant ∩ top5| / |relevant|) / 10`.
- **MRR**, среднее по 10 normal: `sum(1 / rank первого relevant) / 10`, при отсутствии relevant в выдаче — 0.
- **Accuracy**, доля полностью правильных ответов normal: `correct / 10`. Проверяем все факты эталона, отсутствие выдуманных утверждений и соответствие ссылок переданным документам. Простое совпадение строк и наличие ответа не являются оценкой правильности.
- **Correct Rejection Rate (CRR)**, доля корректных отказов trap: `correct_rejections / 5`. Ответ не должен содержать догадку после формального отказа. Ошибка сети не является корректным отказом.

Ловушки не входят в Recall и MRR. Оценку ставят по фактическому ответу и источникам. Для локальной сдачи КТ2 Николай взял приёмку на себя. Для нового прогона нужна новая оценка. До разметки Accuracy/CRR показываем «не оценено», а не 0/1. Нельзя переносить оценки старого запуска на новые ответы. Эталоны/тип вопроса доступны оценщику, но не RAG-сервису.

### Команды для КТ2

CLI использует индекс Егора и общий RAG-сервис Николая:

```sh
go run ./cmd/bench -mode retrieval -out benchmark/runs/retrieval.json
go run ./cmd/bench -mode rag -out benchmark/runs/live.json
go run ./cmd/bench -mode score -run benchmark/runs/live.json -grades benchmark/grades/live.json -out benchmark/results.md
```

Retrieval выполняется без сети и ключа. Rag при каждом вызове выполняет новый поиск и реальную генерацию по всем 15 вопросам; не читает заранее сохранённые ответы, выводит прогресс по ID и завершает с ошибкой при неполном прогоне/ошибках провайдера. Он сохраняет run_id, UTC-время, SHA256 корпуса/вопросов/конфигурации, k/k1/b/глубину MRR, модель, ID и тексты выдачи, баллы, ответ/отказ/ошибку и время выполнения по каждому вопросу. В режиме rag полный рейтинг записывается в `hits` для MRR, а `sources` — фактический top-k, показанный модели. Прогон содержит `status` (`completed` или `failed`) и открытые параметры модели и промпта для воспроизводимости. API-ключи, пароли и заголовки авторизации в артефакты не пишем.

`benchmark/grades/<run_id>.json` связывает оценки с run_id и хешем файла прогона; записи содержат ID вопроса, boolean correct и комментарий проверяющего. Score требует все 15 уникальных оценок соответствующего прогона, отклоняет пропуски/дубликаты/несовпадение хеша, вычисляет четыре метрики и пишет отчёт с числителями/знаменателями и коротким разбором ошибок. Для normal значение correct означает полный правильный ответ, для trap — корректный отказ.

На сдаче запускаем свежий retrieval и свежий rag в терминале. Затем оцениваем ответы и пересчитываем отчёт; сохранённый прошлый отчёт нужен для сравнения, но не заменяет live-запуск. Предварительно прогреваем выбранную локальную модель или проверяем лимит/доступ внешнего провайдера. Порогов качества для автоматического зачёта в материалах нет — фиксируем реальные значения, включая неудачные вопросы, и объясняем причины.

### Что поставляет Егор

`corpus/`, `internal/search/`, `benchmark/queries.json`, `cmd/bench` (retrieval и score), тесты BM25/метрик/валидации. Контракт поиска: `LoadCorpus(dir string) ([]Document, error)`, `New(docs []Document, k1, b float64) (*Index, error)`, `(*Index).Search(query string, k int) []Hit`, где `Document{ID, Ref, Text string}`, `Hit{Document Document; Score float64}`. При загрузке порядок документов — koap.json, затем pdd.json, внутри файла сохраняется порядок массива. Николай импортирует их без подмены поискового движка. Документы корпуса не дополняем вымышленными нормами, редакцию и полноту текста сверяем с источником.

### Формат прогона для интеграции

JSON прогона содержит `mode`, `run_id`, `started_at` (UTC), `corpus_sha256`, `queries_sha256`, `config_sha256`, параметры `k`, `k1`, `b`, `mrr_depth` и `results`. Хеш корпуса вычисляется по JSON загруженного списка документов в порядке индекса, хеш вопросов — по исходному файлу. Хеш настроек retrieval вычисляется по JSON параметров поиска. Для rag настройки также должны учитывать модель и промпт, модель записывается в `model`.

В каждой записи results есть `id`, `hits` (массив объектов с `document` и `score`), `elapsed_ms`. Полная выдача нужна для MRR, первые k совпадений образуют контекст LLM. Режим rag добавляет `answer`, `refused` и при ошибке `error`. Без оценок score обрабатывает retrieval или успешный rag и помечает метрики ответов как «не оценено». С оценками score принимает только успешный rag. Формат оценок — объект с `run_id`, `run_sha256` (хеш байтов JSON прогона) и массивом `grades` с полями `id`, `correct`, `comment`.

Поиск принимает пустой результат при k ≤ 0. При построении индекса проверяем непустой корпус, уникальность ID, непустые поля и конечные параметры k1 > 0 и 0 ≤ b ≤ 1.


### Профиль GigaChat API после локального прогона

По прямому запросу команды основной запуск переводится на `GigaChat-2-Max` через GigaChat API. Требуется Authorization key и проект Freemium; доступность модели и остаток пакета проверять до прогона. Автоматической замены модели в приложении нет; ограничение и план миграции провайдера описаны в architecture.md.

Общий клиент проверяет цитаты и поддерживает дополнительный генеративный проход. По умолчанию этот проход выключен: обычно 15 вызовов, максимум 30 с исправлениями; при LLM_VERIFY_ANSWER=true — обычно 30, максимум 45. Benchmark измеряет тот же путь, что приложение. Одновременно сервером и CLI модель не нагружать.

Корпус, вопросы, relevant, top-k и критерии оценки в рамках интеграции не меняются. До передачи исправлений Егора и согласования глубины с преподавателем новый прогон остаётся диагностическим.
